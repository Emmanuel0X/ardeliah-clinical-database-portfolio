## DEMO 3: REPEATABLE READ: stable snapshot, no phantoms, update conflict error

A's transaction sees one snapshot of the database taken at its first query, however much other sessions commit afterwards.


**Step 1, session A**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) AS doctor_40_bookings_on_1_march
FROM appointment
WHERE doctor_id = 40 AND appointment_date = '2027-03-01' AND status <> 'CANCELLED';
SELECT appointment_id, status FROM appointment WHERE appointment_id = 900002;
```

```text
BEGIN
 doctor_40_bookings_on_1_march 
-------------------------------
                             2
(1 row)

 appointment_id |  status   
----------------+-----------
         900002 | SCHEDULED
(1 row)
```


**Step 2, session B**

> B (autocommit) adds a NEW appointment and changes an existing one.

```sql
INSERT INTO appointment (patient_id, doctor_id, appointment_date, start_time, reason)
VALUES (19991, 40, '2027-03-01', '11:00', 'P3 demo: phantom row');
UPDATE appointment SET status = 'CHECKED_IN' WHERE appointment_id = 900002;
```

```text

UPDATE 1
```


**Step 3, session A**

> Count is unchanged (no PHANTOM ROW) and the status is unchanged (the read is REPEATABLE), although B has already committed both changes. A now tries to change the row that B already changed and committed. A's snapshot is stale for that row, so PostgreSQL refuses rather than silently overwriting (it prevents a LOST UPDATE). The application is expected to catch SQLSTATE 40001 and retry the whole transaction.

```sql

FROM appointment
WHERE doctor_id = 40 AND appointment_date = '2027-03-01' AND status <> 'CANCELLED';
SELECT appointment_id, status FROM appointment WHERE appointment_id = 900002;
UPDATE appointment SET status = 'CANCELLED' WHERE appointment_id = 900002;

```

```text
(1 row)

(1 row)

ROLLBACK
```

> A new transaction takes a new snapshot and sees everything B committed.

## DEMO 8: FOR UPDATE SKIP LOCKED: two lab technicians take different work

Each technician takes the next unassigned request from the work list. With plain FOR UPDATE the second technician would wait for the first; SKIP LOCKED makes them move on to the next free request instead.


**Step 1, session A**

```sql
BEGIN;
SELECT lab_request_id, test_id FROM lab_request
WHERE consultation_id = 900001 AND status = 'REQUESTED'
ORDER BY lab_request_id LIMIT 1
FOR UPDATE SKIP LOCKED;
```

```text
(1 row)
```
